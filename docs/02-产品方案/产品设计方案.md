# 医院后勤工单系统产品设计方案

> 版本：V1.0（完整原型基线）  
> 日期：2026-09-14  
> 覆盖：微信小程序、PC 管理端、UI 原型、UX 流程、交互逻辑、页面状态和验收规则

## 1. 产品目标

以“报修有入口、派单有依据、处理有过程、完工有核验、全程可追溯”为核心，构建报修人、调度管理员、维修人员三角色闭环。产品优先保证工单状态清楚、下一步动作明确、异常可恢复，再提供驾驶舱和绩效运营能力。

移动端以微信小程序交付，并与 PC 端使用统一的视觉规范、状态名称和交互反馈，确保不同角色在工单流转过程中获得一致的信息和操作体验。

## 2. 用户与权限

| 角色 | 核心目标 | 高频任务 | 不能执行 |
|---|---|---|---|
| 报修人 | 快速提交并知道处理到哪一步 | 提交、查询、联系、确认、评价 | 派单、接单、审批延期 |
| 维修人员 | 清楚下一单、时限和处理证据 | 接单、到场、评估、进度、延期、完工 | 修改他人工单、代替报修人确认 |
| 调度/管理员 | 平衡人员负载，控制超时和质量 | 派单、改派、催办、延期审批、配置、统计 | 篡改历史日志和评价 |

## 3. 视觉基线

### 3.1 移动端视觉规范

- 背景：浅灰蓝 `#F3F6F9`，内容卡片白色。
- 主蓝：`#2A62ED / #2A7FF0`；派单紫：`#7A24DF`；处理青：`#2FC8C3`；评价橙：`#FF9800`。
- 成功：绿色；警告/执行中：橙色；超时/错误：红色；关闭：中性灰。
- 卡片：使用 6–14px 圆角和轻阴影，工单卡片左侧使用 4–5px 状态色条。
- 信息：工单编号在首行，时间靠右；标签用短文案，不使用只有颜色没有文字的状态。
- 导航：首页/工作台/我的三栏底部导航；业务详情使用系统导航栏返回。
- 微信小程序保留现有视觉，不调整颜色、卡片和信息层级；仅适配状态栏、胶囊按钮、底部安全区、软键盘和系统授权弹窗。

### 3.2 PC 端视觉规范

- 复用若依深色左侧栏、白色顶部栏、浅灰工作区和 Element UI 控件。
- 主操作使用 `#409EFF`，成功 `#67C23A`，警告 `#E6A23C`，危险 `#F56C6C`。
- 列表采用“查询条件卡 + 操作区 + 表格 + 分页”；详情采用“主信息 + 侧边 SLA/附件”；编辑采用抽屉或对话框。
- 不引入大圆角、渐变玻璃、悬浮 Dock 等与现有后台不一致的视觉语言。

## 7. 核心交互逻辑

### 7.1 提交类动作

- 点击后按钮立即禁用并展示“提交中”，避免重复操作。
- 校验错误显示在字段下方，说明“哪里错、为什么、如何修复”，不只 Toast“参数错误”。
- 网络失败保留表单和已上传文件，提供重试；成功只提示一次并进入详情。
- 派单、改派、退回、延期审批、完工确认是有业务后果的动作，提交前二次确认。

### 7.2 列表与详情

- 默认列表展示角色最需要处理的状态；分段标签带数量。
- 点击卡片任意非按钮区域进入详情；电话、催办等次动作不触发详情跳转。
- 返回列表保留筛选、滚动位置和分页；执行成功后只刷新对应行。
- 工单状态使用“文字 + 颜色”，倒计时低于预警阈值时再增加警告图标。

### 7.3 附件

- 上传前可预览、删除和重拍；单张显示上传进度与失败重试。
- 到场和完工证据必须现场拍摄时，由产品配置是否允许相册选择。
- 查看附件使用全屏预览，显示上传阶段和时间，不暴露原始存储地址。

### 7.4 电话与消息

- 一键电话必须先显示掩码号码和人员姓名，用户确认后调用系统拨号。
- 消息点击进入对应工单/审批详情，并在成功打开后标记已读。
- 失败短信不影响工单操作成功；后台消息记录显示失败原因和重试状态。

## 8. 页面状态规范

每个列表和表单至少实现以下状态：

| 状态 | 设计要求 |
|---|---|
| 初始加载 | 骨架屏保持页面结构，不使用全屏空白转圈 |
| 下拉刷新 | 保留已有内容，顶部展示刷新反馈 |
| 空数据 | 说明为什么为空，提供与场景一致的唯一主动作 |
| 字段校验 | 字段下方红色提示，输入后及时清除 |
| 提交中 | 主按钮禁用、文案变化，禁止重复请求 |
| 成功 | Toast + 页面状态/列表局部刷新，不弹多层对话框 |
| 网络失败 | 保留用户输入，提供重试；可返回时不阻塞导航 |
| 权限不足 | 说明无权限并返回可访问页面，不展示不可执行按钮 |
| 状态冲突 | 告知“工单已被更新”，刷新详情并重算可用动作 |
| 已关闭 | 详情可读、动作禁用，明确关闭原因和时间 |

## 9. 响应式与可访问性

- 移动端基准宽度 375px，适配 320–430px；底部按钮避开安全区。
- 可点击区域不小于 44×44px；重要操作有明确文字，不只用图标。
- PC 端基准 1440×900，最低支持 1280px；表格过宽时固定操作列并横向滚动。
- 状态含义不只依赖颜色；文本和背景满足清晰对比。
- 表单字段有可见标签，必填标记与校验信息可被辅助技术识别。

### 9.1 微信小程序交互约束

| 场景 | 页面行为 | 异常恢复 |
|---|---|---|
| 启动与登录 | 有有效会话时进入角色首页；无会话时进入 M00；第一版继续使用账号、密码和图形验证码 | 会话过期只提示一次，清理会话后回到 M00，保留可重新输入的账号 |
| 自定义首页 | 页面内容避开状态栏和胶囊按钮，现有首页视觉保持不变 | 无法取得窗口信息时使用平台安全区默认值，不遮挡标题和入口 |
| 拍照/选图 | M03、M15、M18 在用户点击后调用相机或相册，展示已选数量、缩略图和上传进度 | 拒绝权限时说明用途并保留表单，可重新授权；必填证据不足时不提交 |
| 到场定位 | M15 在用户点击后获取位置并展示位置摘要和获取时间 | 拒绝或失败时明确提示，可打开设置重试；不得伪造定位成功 |
| 拨打电话 | M13、M19 点击明确的电话号码后调用系统拨号确认 | 号码缺失时禁用入口并说明原因，不读取通讯录 |
| 协议与帮助 | M30 只打开已登记业务域名；可静态交付的协议和帮助优先使用 M31 | 域名或网络不可用时进入 M31 文本内容，不尝试任意外链 |
| 前后台切换 | 从后台回到前台时刷新当前工单版本和可执行动作 | 状态已变化时提示并刷新详情，不继续提交旧动作 |
| 网络中断 | 保留表单、已选附件和筛选现场 | 用户主动重试；派单、完工、确认和评价不得自动重复提交 |
| 页面返回 | 详情返回列表时保留分段、筛选和滚动位置 | 从消息、分享或扫码直达时返回角色首页，不进入无权限页面 |

### 9.2 小程序页面适配要求

- M01/M02/M11 的三栏 TabBar 保持现状，点击区域和底部间距适配小程序安全区。
- M03/M15/M18 的附件组件统一展示选择、压缩、上传、成功、失败和单项重试状态。

### 13.2 工单生命周期与用户下一步

| 待派单 | 报修已提交，尚未指定维修人员 | 调度管理员 | 派单 | 转为“待接单”，通知维修人员 |

| 已关闭 | 业务闭环完成 | 无 | 查看记录 | 进入统计和审计，只读 |
| 已取消 | 派单前被取消 | 无 | 查看原因 | 只读，不再进入调度 |

### 13.3 六条业务闭环

#### 闭环 A：正常报修

1. 报修人登录后从首页“工单申请”进入 M03。
2. 填写类型、位置、故障说明和附件，提交成功后立即得到工单号。
3. 系统进入“待派单”，首页待办和 PC 待派单池同步增加一条。
4. 调度员在 P02/P04 派单，维修人员收到 M20 消息。
5. 维修人员依次接单、到场、评估、处理和完工。
6. 报修人在 M14 核验，通过后在 M09 评价，工单关闭。

闭环标志：报修、派单、到场、处理、确认、评价都有时间、操作人和证据记录。

#### 闭环 B：完工退回

1. 报修人在 M14 查看完工说明和照片。
2. 现场仍有问题时选择“退回处理”，必须填写原因。
3. 工单从“待确认”返回“处理中”，维修人员收到返工消息。
4. 维修人员在 M07 查看退回原因，再次更新进度并提交完工。
5. 报修人重新核验，直到确认通过。

闭环标志：每次提交和退回形成独立处理记录，不能覆盖第一次完工信息。

#### 闭环 C：超时与改派

1. 系统接近 SLA 阈值时，在 M01/P01 显示预警并通知管理员。
2. 管理员进入 P03 查看停留环节、剩余时间和维修人员负载。
3. 管理员可催办；人员无法继续处理时，通过 P04 改派并填写原因。
4. 原处理人收到撤回消息，新处理人收到派单消息，报修人进度页同步显示改派节点。

闭环标志：超时是工单的风险标记，不会把“处理中”强行改成另一主状态。

#### 闭环 D：延期审批

1. 维修人员在 M17 看见原截止时间和剩余时长，提交新时间、原因和佐证。
2. 申请期间仍按原截止时间计时，避免申请本身自动停止 SLA。
3. 管理员从消息、P03 或 P11 进入审批：同意时展示“旧时间 → 新时间”，拒绝时必须填写原因。
4. 审批结果通知维修人员，并写入报修人的 M13 时间线。

闭环标志：申请、审批、原截止、新截止和原因均可审计。

#### 闭环 E：通知失败

1. 工单业务动作先成功落库，页面正常提示操作成功。
2. 短信失败不回滚工单，P09 显示失败原因和重试状态。
3. 系统自动重试；达到上限后转人工处理，站内消息仍保留。

闭环标志：业务成功与外部短信稳定性解耦，但每条通知最终有明确成功或失败结果。

#### 闭环 F：评价与运营改进

1. 报修人对已完成工单进行星级和文字评价。
2. 评价完成后工单关闭，不能重复评价。
3. P08 汇总及时率、满意度、返工率等指标。
4. 管理员依据低分原因调整分类规则、人员安排和消息模板。

闭环标志：评价不只是展示，而是进入人员绩效和服务改进统计。

## 14. 移动端逐页 UI 与 UX 使用说明

### 14.1 M00 登录

![M00 登录](ui/mobile/01-入口与工作台/m00-login-existing.png)

**使用者与入口**：所有角色首次打开应用或登录失效时进入。

**页面区域**：上方品牌/标题，中部账号、密码、验证码输入区，下方登录按钮和协议/帮助入口。密码默认隐藏，验证码可点击刷新。

**使用步骤**：输入账号和密码 → 输入验证码 → 点击“登录”。登录成功后，系统根据角色进入 M01 首页，并加载其菜单权限和待办数量。

**校验与异常**：账号为空、密码为空、验证码为空分别在对应输入框下提示；密码错误时保留账号、清空密码；连续失败达到阈值后短时限制；网络失败保留所有非敏感输入并允许重试。登录按钮在请求期间禁用。

**离开页面**：成功进入 M01；点击帮助进入常见问题；登录失败停留本页。

### 14.2 M01 首页看板

![M01 首页看板](ui/mobile/01-入口与工作台/m01-dashboard-existing.png)

**使用者与目标**：登录后的所有角色，用一屏知道“今天发生了什么、我现在要做什么”。

**页面区域**：今日申报/完成统计、工单趋势、工单申请/派发/处理快捷入口、各状态数量、底部首页/工作台/我的导航。

**交互逻辑**：点击统计数字进入对应筛选后的列表；点击趋势的日/周/月切换时间范围；快捷入口根据权限显示，无派单权限的用户不展示“工单派发”；下拉刷新同时刷新统计、趋势和待办。

**数据状态**：首次加载使用骨架屏；局部统计失败时保留其他区块并显示“点击重试”，不让整页不可用；所有数字来自真实接口，不使用随机数或模拟延时。

**流程去向**：工单申请 → M03；工单派发 → M04；工单处理 → M06；底部导航 → M02/M11。

### 14.3 M02 工作台

![M02 工作台](ui/mobile/01-入口与工作台/m02-workbench-prototype.png)

**使用者与目标**：需要集中处理待办的调度员和维修人员；普通报修人看到与自己有关的申请、待确认和待评价入口。

**页面区域**：常用工作快捷区、待办数量、超时预警、最近工单。页面延续首页白卡片和蓝/紫/青/橙状态色。

**交互逻辑**：待办卡点击后带入对应状态筛选；最近工单只展示 3–5 条，点击进入详情；红点只表示未处理数量，进入列表不自动清零，完成业务动作后才减少。

**角色差异**：管理员显示待派单、延期审批、超时预警；维修人员显示待接单、执行中、退回处理；报修人显示处理中、待确认、待评价。

### 14.4 M03 工单提交

![M03 工单提交](ui/mobile/02-报修与进度/m03-submit-existing.png)

**使用者与入口**：报修人从 M01/M02 进入。

**页面内容**：报修类型、位置、联系电话、紧急程度、故障说明、附件。联系电话默认带入个人资料；位置可从常用地点选择，也可手输；附件显示张数、上传进度和删除操作。

**使用步骤**：选择类型 → 确认位置和电话 → 描述故障 → 上传照片 → 点击“提交工单” → 二次确认关键信息 → 成功页显示工单号并进入 M13。

**规则**：类型、位置、联系电话、故障说明必填；联系电话格式校验；故障说明限制 500 字；普通工单附件可选，紧急类别是否强制照片由分类规则决定；一次最多 9 张，每张大小由配置控制。

**异常恢复**：单张上传失败只重试该张；提交失败保留表单和已上传文件；重复点击使用同一幂等键，不产生重复工单；成功后清除草稿。

### 14.5 M12 我的工单

![M12 我的工单](ui/mobile/02-报修与进度/m12-my-orders-prototype.png)

**使用者与入口**：报修人从“我的”或首页统计进入，用于查找自己提交的全部工单。

**页面区域**：全部/待处理/处理中/已完成分段、工单号/故障关键字搜索、工单卡片。卡片显示编号、类型、位置、当前状态、处理人和预计完成时间。

**交互逻辑**：切换分段立即刷新列表；搜索采用提交搜索，不在每输入一个字时请求；下拉刷新，触底加载下一页；点击卡片进入 M13。

**空状态**：对应分段无数据时使用 M21；从空状态可直接进入 M03。加载失败保留旧列表并提供重试。

![M13 工单进度](ui/mobile/02-报修与进度/m13-progress-prototype.png)

**使用者与目标**：报修人了解工单当前由谁处理、是否超时、发生过哪些动作。

**交互逻辑**：筛选条件写入 URL，进入详情再返回时完整恢复；点击编号进入 P03；待派单显示“派单”，已派显示“改派/催办”，关闭工单只显示“查看”；导出前显示当前筛选范围和预计条数。

**权限**：不同部门管理员只看到数据范围内的工单；无操作权限时不显示按钮，但仍由后端再次校验。

### 15.3 P03 工单详情

![P03 工单详情](ui/pc/02-工单管理/p03-order-detail-prototype.png)

**使用者与目标**：管理员在一个页面完成诊断、跟踪和异常处理。

**页面区域**：基本信息、当前状态、SLA 卡、附件、当前处理人、完整时间线，以及催办/改派/延期审批等动作。

**交互逻辑**：时间线可展开每个动作的说明和附件；SLA 低于阈值显示橙色，已超时显示红色；改派打开 P04；延期申请出现审批卡，审批时展示旧/新截止时间。

**审计要求**：页面不提供修改历史动作的入口；所有管理动作必须填写原因并进入时间线。

### 15.4 P04 派单/改派抽屉

![P04 派单抽屉](ui/pc/02-工单管理/p04-dispatch-prototype.png)

**使用者与入口**：管理员从 P02 或 P03 点击派单/改派后，在当前页面右侧打开，保持列表或详情上下文。

**页面区域**：工单摘要、派单方式、处理人员、人员推荐、完成时限、备注和确认按钮。

**交互逻辑**：选择人员后展示其状态、当前负载和同类工单表现；改派时额外显示原处理人和改派原因；提交前二次确认；成功关闭抽屉并局部刷新原页面。

**冲突**：其他管理员已处理时，抽屉停止提交并刷新工单状态，不允许覆盖。

### 15.5 P05 维修人员状态

![P05 人员状态](ui/pc/03-人员调度/p05-engineers-prototype.png)

**使用者与目标**：调度员查看人员在线状态、专业、负载和服务表现，为派单提供依据。

**页面区域**：在线/空闲/处理中/离线统计，专业和状态筛选，人员卡片/列表，联系与派单动作。

**交互逻辑**：点击当前工单数打开该人员在办工单；点击派单进入工单选择或从 P04 返回；状态长时间未更新时显示“心跳过期”。

### 15.6 P06 分类与 SLA

![P06 分类与 SLA](ui/pc/04-基础配置/p06-sla-config-prototype.png)

**使用者与目标**：系统管理员维护报修分类、响应时限、完成时限、默认专业和预警规则。

**交互逻辑**：新增/编辑规则时预览“某类普通工单提交于 10:00，将在何时预警和超时”；停用分类前提示仍有多少历史工单引用；修改规则只影响新工单。

**规则**：分类编码创建后不可随意更改；响应时限不能大于完成时限；规则生效时间不能与同分类、同紧急度已有规则重叠。

### 15.7 P07 报修人员管理

![P07 报修人员管理](ui/pc/04-基础配置/p07-users-prototype.png)

**使用者与目标**：账号管理员维护报修人员身份、组织和账号状态，并查看报修概况。

**页面区域**：姓名/手机号/组织/状态筛选，人员列表，新增、导入、编辑、重置密码和详情。

**交互逻辑**：复用若依用户管理流程；详情增加累计报修、处理中、最近报修和评价情况；停用账号前提示其未完成工单，但不删除历史记录。

### 15.8 P08 维修绩效分析

![P08 绩效分析](ui/pc/05-统计分析/p08-performance-prototype.png)

**使用者与目标**：主管按时间、组织、专业和人员评估服务效率与质量。

**指标**：完成量、平均响应时长、平均到场时长、按时完成率、满意度、返工率。每个指标明确分母、排除条件和统计时间。

**交互逻辑**：图表和明细共用筛选条件；点击人员柱状图过滤明细；导出内容与当前筛选一致；样本量过小时同时显示数量，避免只看百分比误判。

### 15.9 P09 消息模板与发送记录

![P09 消息管理](ui/pc/06-消息与短信/p09-messages-prototype.png)

**使用者与目标**：管理员配置派单、接单、超时、延期、完工和评价通知，并追踪发送结果。

**页面区域**：模板分类树，模板编辑，变量说明，预览，发送记录，失败重试。

**交互逻辑**：保存前使用示例数据预览最终文本；不允许使用未知变量；模板停用时明确影响哪些事件；发送记录可按工单号追踪到业务详情。

### 15.10 P10 短信账户

![P10 短信账户](ui/pc/06-消息与短信/p10-sms-prototype.png)

**页面区域**：可用短信数、今日发送/失败、本月发送，余额预警和失败重试开关，供应商配置掩码，最近发送记录。

**安全与交互**：访问密钥永不明文回显；修改密钥需重新输入并二次确认；余额低于阈值时在 P01 和消息中心提醒；刷新余额失败时展示上次成功更新时间。

### 15.11 P11 延期审批

![P11 延期审批](ui/pc/02-工单管理/p11-delay-approval-prototype.png)

**使用者与目标**：调度管理员集中处理维修人员提交的延期申请，明确比较原截止时间、新截止时间和申请理由。

**页面区域**：申请状态筛选、工单或申请人关键字、延期申请表格、同意和拒绝动作、拒绝原因对话框及分页。

**交互逻辑**：默认显示待审批申请；查询条件同步到页面地址。点击同意先进行二次确认，成功后该行立即变为“已同意”；点击拒绝必须填写原因，未达到 2 个字符不能提交。申请已被其他管理员处理或工单已完工时，页面提示状态已变化并刷新列表。

**状态反馈**：待审批使用警示色，已同意使用成功色，已拒绝使用错误色，因工单完工自动取消的申请使用中性色。历史记录只读，不再显示审批按钮。

### 15.12 P12 SLA 规则

![P12 SLA 规则](ui/pc/04-基础配置/p12-sla-rules-prototype.png)

**使用者与目标**：授权管理员维护新工单使用的 SLA 匹配规则，不改变历史工单已保存的截止时间。

**页面区域**：规则名称或编码、适用分类、紧急程度和状态筛选，规则列表，新增/编辑对话框，以及启用/停用动作。

**交互逻辑**：新增时填写编码、名称、适用范围、紧急程度、优先级、生效区间、响应/到场/完成时限、预警提前量和延期许可；页面根据填写值预览截止时间。编辑时编码锁定。启用和停用都需确认；启用前如果有效期与同范围、同紧急度、同优先级规则重叠，页面展示后端返回的冲突原因并保留表单。

**历史规则**：已被工单引用的规则仍可编辑或停用，列表显示引用数量。保存只改变后续新建工单的匹配结果，已有工单继续使用创建时快照。

## 16. 跨页面 UX 规则

### 16.1 页面主动作唯一

每个状态只突出一个最需要完成的主动作：待派单突出“派单”，已接单突出“到场确认”，处理中突出“提交完工”，待确认突出“确认完工”。催办、电话、取消等保持次要层级，防止用户不知道下一步。

### 16.2 返回与现场保留

- 移动端从列表进入详情后返回，保留原分段和滚动位置。
- PC 从筛选列表进入详情后返回，保留 URL 查询条件、页码和排序。
- 表单因网络失败或误返回时提示保存草稿，避免用户重新输入。

### 16.3 消息与页面状态一致

消息只是入口，不是状态事实。用户从旧消息进入时，以最新详情状态为准；如果动作已被完成，页面展示最新结果并隐藏过期按钮。

### 16.4 多人并发

派单、接单、延期审批和完工确认可能被多人同时操作。先成功者生效；后提交者看到“状态已变化”，系统刷新页面并解释是谁在何时完成了该动作。

## 17. 客户验收场景

客户验收时不只逐页看图，应按以下脚本走完整闭环：

1. **正常闭环**：M03 提交 → M04/M05 派单 → M06/M07 接单 → M15 到场 → M16 评估 → M18 完工 → M14 确认 → M09 评价 → M10 查看。
2. **退回闭环**：完工后 M14 退回 → M07 显示原因 → 再次完工 → 再次确认。
3. **延期闭环**：M17 申请 → P11 审批 → M13/M07 同步新截止时间和审批记录。
4. **改派闭环**：P03/P04 改派 → 原人员工单移除 → 新人员收到消息 → M13 出现改派节点。
5. **超时闭环**：临近超时 → M01/P01 预警 → 催办或改派 → P08 正确统计。
6. **异常恢复**：上传失败、网络失败、重复提交、状态冲突、短信失败分别验证页面反馈和数据不重复。
7. **账户闭环**：M00 注册入口 → M22 注册 → M00 登录 → M11 → M24 查看资料 → M25 修改资料 → M23 修改头像。
8. **安全设置闭环**：M11 → M27 → M26 修改密码 → M00 重新登录；再次登录确认新密码生效、旧密码失效。
9. **帮助与协议闭环**：M11 → M28 → M31 阅读帮助；M11/M27 → M29 → M30 阅读协议并返回原页面。

只有上述九类场景都能从入口走到明确终态，并在页面状态、时间线、通知和统计中相互对应，产品才算真正闭环。
